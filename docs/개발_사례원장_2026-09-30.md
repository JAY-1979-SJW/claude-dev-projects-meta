# 개발 사례 원장 — 실제로 겪은 오류와 재발 방지 (2026-09-30 haehan-ai-orchestrator 세션)

**목적:** 새 프로젝트를 시작할 때 같은 오류를 처음부터 막는다. 이 문서는 **사실 기록**이며 그 자체로 검사를 강제하지 않는다.
강제 조항 후보는 `개발_사례원장_강제조항후보_2026-09-30.md`에 따로 둔다(검증 전에는 `rules.toml`에 넣지 않는다).

**사용법**
- `/new-project-standard` 0단계 질문 **Q4("유사 프로그램에서 겪은 문제")** 에 이 원장의 관련 CASE 를 후보로 제시하고, 사용자가 고른 것을
  `project-scope.md` §4 (CASE-n) 로 옮긴다. 총괄 기준서 §5 공통 규칙의 근거로 쓴다.
- 새 프로젝트 골격을 만들 때는 아래 **"착수 체크리스트"** 를 먼저 훑는다.

**공개 여부:** 이 문서는 공개 저장소(`claude-dev-projects-meta`)에 올라간다. 보안 약점의 구체적 재현 방법·계정·키·고객 정보는 적지 않는다(적으면 안 된다). 필요하면 비공개 문서로 분리한다.

**표기:** 각 사례는 `증상 → 원인 → 재발 방지 → 탐지 방법` 순. 확인하지 못한 것은 `[미확인]`. 프로젝트별 고유 사정은 `적용 유형`으로 구분
(A=모든 프로젝트, S=서버, D=데스크톱/브라우저 자동화, W=웹 크롤링/자동화, P=Python).

## 착수 체크리스트 (새 프로젝트 첫날)

1. [ ] 저장소 공개 여부를 먼저 정한다. **공개면** 시크릿 스캔(gitleaks)·이슈 내용 점검·러너 종류를 그에 맞춘다 (CASE-01, 30, 31)
2. [ ] `master` 브랜치 보호(CI 통과 필수) + CI 를 **GitHub 서버 러너**로 시작한다 (CASE-02, 03)
3. [ ] 테스트 `conftest.py` 에 **실제 사용자 데이터 경로를 임시 경로로 돌리는 autouse 픽스처**를 첫 커밋에 넣는다 (CASE-12, 13)
4. [ ] `requirements.txt` 는 **깨끗한 가상환경에서** 설치해 테스트가 통과하는지 확인한다 (CASE-06)
5. [ ] 상태 파일·비밀번호는 평문/키-옆-보관 금지, OS 자격 증명 저장소 사용 (CASE-14, 15)
6. [ ] 모듈을 쪼갤 때는 옛 이름 재수출(파사드) + 옛 이름을 참조하는 테스트를 같이 확인한다 (CASE-08, 16)
7. [ ] 브라우저 자동화면 **연결은 프로세스당 하나**, 새 연결을 호출마다 맺지 않는다 (CASE-23)
8. [ ] 경고 억제 주석(`nosec`, `noqa`)은 **도구가 지목하는 줄**에 두고, 커밋 후 다시 측정한다 (CASE-18)
9. [ ] 자동 생성 파일(레지스트리·잠금 파일)은 손으로 병합하지 않고 **정본 도구로 재생성**한다 (CASE-21)
10. [ ] "통과"를 보고하기 전에 **실제로 실행**한다. 합성 데이터 통과는 실제 화면 통과가 아니다 (CASE-26, 27)
